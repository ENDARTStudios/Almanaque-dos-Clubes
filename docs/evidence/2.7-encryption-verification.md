# Evidência 2.7 — Criptografia (argon2id senha + SHA-256 token)

**Data:** 2026-07-20
**Responsável:** Doer (GLM-5.1)

---

## Objetivo

Criar helpers de criptografia para:
1. **Senhas:** argon2id (RFC 9106) com custo 12, 64 MiB de memória
2. **Tokens:** SHA-256 (rápido, adequado para tokens de alta entropia)
3. **Comparações timing-safe** para prevenir timing attacks

## Implementação

### Arquivo: `apps/api/src/config/crypto.ts`

Funções exportadas:

| Função | Propósito | Latência típica |
|--------|-----------|-----------------|
| `hashPassword(plaintext)` | Gera hash argon2id com salt aleatório embutido | ~100-150ms |
| `verifyPassword(plaintext, hash)` | Verifica senha contra hash (timing-safe) | ~100-150ms |
| `generateToken()` | Gera 32 bytes aleatórios (base64url, ~43 chars) | <1ms |
| `hashToken(token)` | Hash SHA-256 hex (64 chars) de um token | <1ms |
| `verifyToken(token, hash)` | Compara token contra hash (timing-safe) | <1ms |
| `generateNumericCode(length)` | Gera código OTP numérico (4-10 dígitos) | <1ms |
| `safeEqual(a, b)` | Comparação timing-safe de strings | <1ms |

### Parâmetros do argon2id (RFC 9106)

```typescript
const ARGON2_OPTIONS: HashOptions = {
  type: argon2.argon2id,     // = 2 — combina resistência a GPU (i) e trade-offs (d)
  memoryCost: 65_536,        // 64 MiB — resistente a GPU/ASIC
  timeCost: 12,              // 12 iterações
  parallelism: 1,            // 1 thread (custo de hardware para atacante)
};
```

**OWASP recomenda:** argon2id com `m=46 MiB`, `t=1`, `p=1` para servidores típicos. Nós usamos `m=64 MiB`, `t=12` (mais conservador). Latência ~100ms por hash é aceitável para login (humano espera 200-500ms anyway).

## Decisões técnicas

### 1. Senha usa argon2id; Token usa SHA-256

**Senha:** precisa de KDF memory-hard porque usuário escolhe senha de baixa entropia. argon2id força atacante a alocar 64 MiB por hash testado → inviável paralelizar em GPU.

**Token:** já é alta-entropia (32 bytes = 256 bits aleatórios). Não precisa de KDF. SHA-256 é seguro porque:
- Hash unidirecional: se banco vazar, atacante não recupera o token
- Rápido (~1μs): importante para `/auth/refresh` (hot path)
- Preimage attack requer 2^256 tentativas — computacionalmente impossível

### 2. Salt embutido no hash (não persistido separado)

O `argon2.hash()` retorna uma string codificada que inclui salt, parâmetros e hash:
```
$argon2id$v=19$m=65536,t=12,p=1$<salt-base64>$<hash-base64>
```

Persistimos essa string única em `users.passwordHash`. Não há coluna `salt` separada — simplifica schema e evita bugs de desync.

### 3. `verifyPassword` captura exceções de hash malformado

```typescript
export async function verifyPassword(plaintext: string, hash: string): Promise<boolean> {
  if (!plaintext || !hash) return false;
  try {
    return await argon2.verify(hash, plaintext);
  } catch {
    return false;  // Hash malformado → trata como falha, não propaga
  }
}
```

Importante para robustez: se um hash corrompido entrar no banco, `verifyPassword` retorna `false` em vez de quebrar a request.

### 4. `verifyToken` usa `timingSafeEqual`

```typescript
const a = Buffer.from(computedHash, 'hex');
const b = Buffer.from(hash, 'hex');
if (a.length !== b.length) return false;
return timingSafeEqual(a, b);
```

Previne timing attacks que poderiam inferir o hash correto observando o tempo de comparação.

### 5. `generateNumericCode` separado de `generateToken`

Códigos OTP (6 dígitos) têm baixa entropia (~20 bits) — adequados apenas para:
- Verificação por email/SMS de curta duração (15 min)
- Lockout após 3-5 tentativas

NÃO usar como refresh token ou API key (use `generateToken()` nesses casos).
