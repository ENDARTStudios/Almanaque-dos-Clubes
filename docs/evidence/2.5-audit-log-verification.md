# Evidência 2.5 — AuditLog (append-only, com redaction de sensíveis)

**Data:** 2026-07-20
**Responsável:** Doer (GLM-5.1)

---

## Objetivo

Garantir que o `AuditLog` seja **somente insert** (sem update/delete), com tipagem forte de ações e entidades, e que campos sensíveis (senha, token, secret) sejam automaticamente mascarados antes de persistir.

## Implementação

### Arquivo: `apps/api/src/modules/audit/audit-log.service.ts`

Helper exportado como `auditLog` (singleton de serviço) com:

- **`auditLog.record(input)`** — insere um registro (única forma de escrita)
- **`auditLog.listByEntity(entityType, entityId)`** — busca por entidade (admin dashboard)
- **`auditLog.listByUser(userId)`** — busca por usuário (histórico de atividade)
- **`auditLog.countByAction(action, since)`** — conta eventos por ação (dashboard segurança)

### Constantes tipadas

- `AuditAction` — 23 ações padronizadas em formato `<entity>.<verb>`:
  - `user.register`, `user.login`, `user.login_failed`, `user.logout`, `user.refresh`
  - `user.password_reset.request`, `user.password_reset.confirm`, `user.password_changed`
  - `user.email_verified`, `user.suspended`, `user.reactivated`
  - `role.assigned`, `role.revoked`, `permission.denied`
  - `subscription.created`, `subscription.cancelled`, `subscription.plan_changed`
  - `billing.paid`, `billing.refunded`, `billing.failed`
  - `entity.create`, `entity.update`, `entity.delete`

- `EntityType` — 10 tipos de entidade auditáveis: `User`, `Club`, `Player`, `Competition`, `Ranking`, `Session`, `Subscription`, `Billing`, `Role`, `Permission`

### Redaction automática

A função `redactSensitive()` recursivamente percorre `changes` e `metadata` e substitui por `'***REDACTED***` qualquer campo cujo nome (case-insensitive) esteja na lista:

```
password, passwordhash, token, tokenhash, refreshtoken, accesstoken,
secret, apikey, authorization, cookie
```

### Falha resiliente

Em **produção**: se o insert no AuditLog falhar (ex.: banco indisponível), o erro é logado mas não propaga — a request principal não pode falhar por causa de auditoria.

Em **desolvimento**: o erro é relançado para pegar bugs cedo (princípio fail-fast).

## Decisões técnicas

### 1. SQLite: `String?` em vez de `Json?`
Prisma 5.22 não suporta `Json?` nativamente no connector SQLite (erro P1012: "The current connector does not support the Json type"). Solução:
- Schema SQLite: `changes String?` e `metadata String?`
- Schema PostgreSQL: `changes Json?` (JSONB nativo) e `metadata Json?` (JSONB)
- Service detecta o provider via `process.env.PRISMA_SCHEMA_PROVIDER` e serializa com `JSON.stringify` apenas no caso SQLite

### 2. `auditLog.user` com `onDelete: SetNull`
Mesmo se um usuário for deletado, queremos preservar o histórico de auditoria. `SetNull` mantém o registro com `userId = null`.

### 3. Não há interface de update/delete no service
O objeto `auditLog` exportado tem apenas `record`, `listByEntity`, `listByUser`, `countByAction`. Confirmado via type check: `auditLog.update === undefined`, `auditLog.delete === undefined`, `auditLog.deleteMany === undefined`. Isso impede uso acidental.

### 4. Índice composto `@@index([entityType, entityId])`
Permite buscar rapidamente todos os eventos de auditoria de uma entidade específica (ex.: "histórico do clube X") sem table scan.
