# Evidência 2.8 — Session helper (create/verify/revoke)

**Data:** 2026-07-20
**Responsável:** Doer (GLM-5.1)

---

## Objetivo

Criar helper para gerenciar sessões de autenticação (refresh tokens):
- `createSession` — gera novo refresh token + persiste
- `verifySession` — verifica se token corresponde a sessão ativa
- `revokeSession` — revoga uma sessão (logout)
- `revokeAllUserSessions` — revoga todas as sessões de um usuário (password reset, comprometimento)
- `countActiveUserSessions`, `listActiveUserSessions` — dashboard
- `cleanupExpiredSessions` — job de manutenção

## Decisões técnicas

### 1. Refresh token nunca persistido em texto
Persistimos apenas `tokenHash` (SHA-256 do token). Se o banco vazar:
- Atacante não consegue recuperar os tokens originais
- Não consegue forjar refresh tokens válidos
- Hash SHA-256 com input de 32 bytes aleatórios é computacionalmente seguro

### 2. `revokedAt: null` em vez de deletar o registro
Revogar = marcar `revokedAt = now`, NÃO `delete`. Vantagens:
- **Auditoria:** sabemos quando a sessão foi revogada
- **Detecção de reuso:** se `verifySession` recebe token de sessão revogada, sabemos que o token foi roubado (comprometimento)
- **Queries:** índice `@@index([userId, revokedAt])` permite buscar "sessões ativas" rapidamente sem table scan

### 3. `revokeSession` é idempotente
Usa `updateMany` com `where: { tokenHash, revokedAt: null }` — não falha se já está revogada. Retorna `true` mesmo se nada foi atualizado.

### 4. `verifySession` retorna `null` para TODOS os casos de falha
- Token inexistente → null
- Sessão revogada → null
- Sessão expirada → null
- Token vazio → null

A rota `/auth/refresh` não consegue distinguir entre eles — e **não deve**. Mensagem de erro sempre genérica "Credenciais inválidas" (Tarefa 3.3).

### 5. `listActiveUserSessions` não retorna `tokenHash`
```typescript
select: {
  id: true,
  userAgent: true,
  ipAddress: true,
  expiresAt: true,
  createdAt: true,
  // NÃO inclui tokenHash
}
```
Mesmo em painel admin, não há razão para expor hashes de tokens.

### 6. `cleanupExpiredSessions` (job futuro)
- Retenção 30 dias (configurável)
- Deleta `WHERE expiresAt < now - 30d`
- Será chamado por cron diário na Fase 9 (CI/CD e deploy)
- Mantém tabela `sessions` enxuta mesmo com 50k+ usuários
