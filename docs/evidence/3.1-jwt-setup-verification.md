### Arquivo: `apps/api/src/modules/auth/jwt.service.ts` (criado)

**Tipos exportados:**
- `AccessTokenPayload`: `{ sub, email, roles, permissions, type: 'access' }`
- `RefreshTokenPayload`: `{ sub, sessionId, type: 'refresh' }`
- `AuthUser`: `{ id, email, roles, permissions }` (anexado a `request.user`)

**Constantes:**
- `ACCESS_COOKIE_NAME_DEV = 'access_token'`, `REFRESH_COOKIE_NAME_DEV = 'refresh_token'`
- `ACCESS_COOKIE_NAME_PROD = '__Host-access_token'`, `REFRESH_COOKIE_NAME_PROD = '__Host-refresh_token'` (prefix RFC 6265bis)
- `ACCESS_TOKEN_MAX_AGE_SECONDS = 900` (15 min)
- `REFRESH_TOKEN_MAX_AGE_SECONDS = 604800` (7 dias)

**Funções:**
- `getAccessCookieName(isProd)` — dev: `access_token`, prod: `__Host-access_token`
- `getRefreshCookieName(isProd)` — idem para refresh
- `getCookieOptions(isProd, maxAgeSeconds?)` — `{ httpOnly: true, secure: isProd, sameSite: 'strict', path: '/', maxAge? }`
- `createJwtService(app)` — factory que retorna `JwtService` com `signTokens`, `verifyAccessToken`, `verifyRefreshToken`

### Arquivo: `apps/api/src/types/fastify.d.ts` (criado)

Augmentation de tipos via declaration merging:

```typescript
declare module 'fastify' {
  interface FastifyInstance {
    jwt: JWT;
  }
  interface FastifyRequest {
    user?: AuthUser;
  }
}

declare module '@fastify/jwt' {
  interface FastifyJWT {
    payload: AccessTokenPayload | RefreshTokenPayload;
    user: AuthUser;
  }
}
```

Permite que TypeScript saiba que `app.jwt` existe e `request.user` é `AuthUser | undefined`.

Adicionado `src/**/*.d.ts` ao include para garantir que `fastify.d.ts` seja carregado:

## Decisões técnicas

### 1. Defesa em profundidade: campo `type` no payload
```typescript
if (payload.type !== 'access') return null;
```
Mesmo se JWT_SECRET e JWT_REFRESH_SECRET fossem iguais (o que validamos em prod que NÃO são), um access token não poderia ser usado como refresh e vice-versa. Camada extra de proteção.

### 2. Prefix `__Host-` em produção (RFC 6265bis)
Cookies com prefix `__Host-` exigem:
- `Secure: true` (só HTTPS)
- `Path: /` (raiz)
- Sem `Domain` (não enviado para subdomínios)

Previne subdomain takeover attacks onde atacante controla subdomínio e captura cookie.

### 3. `SameSite=Strict`
Cookies NÃO são enviados em cross-site requests. Previne CSRF:
- Site malicioso tenta POST para `/api/v1/checkout` → cookie NÃO enviado → 401.

### 4. `verify.algorithms: ['HS256']`
Previne algorithm confusion attack onde atacante forja token com `alg: 'none'` ou RS256 com chave pública HMAC. Whitelist explícita de HS256.

### 5. `signed: false` no cookie do JWT
`@fastify/jwt` suporta cookies signed (HMAC) além do JWT assinado. Como o JWT já é assinado (HMAC SHA-256), assinar o cookie seria redundante. `signed: false` desativa.

### 6. Refresh token usa o mesmo `app.jwt.sign` com `expiresIn` diferente
@fastify/jwt v10 registra um único secret por instância. Refresh token idealmente teria secret diferente, mas isso requereria registrar segundo plugin (`@fastify/jwt` com namespace). Por simplicidade nesta tarefa, ambos usam o mesmo secret — mas o campo `type` no payload previne confusão. Tarefa 3.3 pode refinar registrando segundo plugin com `namespace: 'refresh'` se necessário.

### 7. `createJwtService(app)` factory
Em vez de exportar funções soltas, criamos um factory que pega `app` e retorna o serviço vinculado à instância Fastify. Vantagem:
- Service tem acesso a `app.jwt.sign` e `app.jwt.verify`
- Tipagem forte: `JwtService` interface define contrato
- Facilita mocks em testes (pode criar service fake)
