## Objetivo

Implementar rotas de autenticação completas:
- `POST /auth/register` — cria usuário com hashPassword (argon2id), emite access + refresh tokens, seta cookies httpOnly
- `POST /auth/login` — verifica verifyPassword, emite tokens, msg genérica "Credenciais inválidas"
- `POST /auth/logout` — revoga Session no banco (revokeSession), limpa cookies
- `POST /auth/refresh` — rotação de refresh token (invalida antigo, emite novo par)

## Implementação

### Arquivos criados

#### `apps/api/src/modules/auth/auth.schemas.ts`

Schemas Zod para validação de entrada:
- `RegisterSchema`: email (normalizado lowercase), senha (mín 8, máx 128, regex para 1 minúscula + 1 maiúscula + 1 dígito), name opcional (2-100 chars)
- `LoginSchema`: email + senha (mín 1, máx 128)
- `RefreshSchema`: objeto opcional com `refreshToken` (para testes; em produção vem do cookie)

#### `apps/api/src/modules/auth/auth.service.ts`

Camada de serviço com orquestração:
- `register(input, metadata)` — cria User com argon2id, atribui role FREE, cria subscription FREE, cria sessão, registra audit log
- `login(input, metadata)` — busca usuário, verifica senha com timing-safe (DUMMY_HASH se não existe), atualiza lastLoginAt, cria sessão
- `logout(refreshToken)` — revoga sessão, idempotente
- `refreshSession(oldRefreshToken, metadata)` — verifica token antigo, revoga, cria novo, detecta reuso (revoga TODAS as sessões se token revogado for usado novamente)
- `extractMetadata(request)` — extrai IP + User-Agent

Erros customizados:
- `AuthError` (401, INVALID_CREDENTIALS) — genérico
- `ConflictAuthError` (409, EMAIL_ALREADY_REGISTERED) — para register
- `ValidationAuthError` (422, VALIDATION_ERROR) — para Zod errors

#### `apps/api/src/modules/auth/auth.routes.ts`

Rotas Fastify:
- `POST /auth/register` — Zod valida → service register → JWT sign → setAuthCookies → 201 com `{ data: { user: { id, email, roles } } }`
- `POST /auth/login` — Zod valida → service login → JWT sign → setAuthCookies → 200 com user
- `POST /auth/logout` — extrai refresh token do cookie → service logout → clearAuthCookies → 200
- `POST /auth/refresh` — extrai refresh token → service refreshSession → JWT sign → setAuthCookies → 200

Helpers internos:
- `setAuthCookies(reply, accessToken, refreshToken)` — seta 2 cookies httpOnly com opções seguras
- `clearAuthCookies(reply)` — limpa cookies (Max-Age=0)
- `getRefreshTokenFromRequest(request)` — lê cookie OU body (para testes)
- `handleAuthError(err, reply)` — traduz AuthError/ConflictAuthError/ValidationAuthError/ZodError em respostas HTTP coerentes

### `apps/api/src/app.ts` (atualizado)

Registradas `authRoutes` no prefix `/api/v1`:

## Decisões técnicas

### 1. Timing-safe login (DUMMY_HASH)
Se email não existe no banco, ainda chamamos `verifyPassword(input.password, DUMMY_HASH)` para gastar tempo similar ao caso de usuário existente (~100ms). Previne timing attack que poderia revelar se email está cadastrado.

### 2. Mensagem genérica "Credenciais inválidas"
Login falho retorna SEMPRE a mesma mensagem, seja:
- Email não existe
- Senha errada
- Usuário suspenso (status !== 'ACTIVE')

Atacante não consegue distinguir entre eles pela resposta.

### 3. Refresh token rotation
Cada `/auth/refresh`:
1. Verifica token antigo contra `Session` ativa
2. Revoga sessão antiga (marca `revokedAt = now`)
3. Cria nova sessão com novo refresh token
4. Retorna novo par (access + refresh)

**Defesa contra roubo de token:** se atacante roubar refresh token e usá-lo DEPOIS do usuário legítimo já ter rodado, o token antigo será detectado como "reuso de token revogado" → sistema revoga TODAS as sessões do usuário (forçando novo login).

### 4. Senha forte exigida no register
Regex exige: mín 8 chars, 1 minúscula, 1 maiúscula, 1 dígito. Não exigimos símbolos especiais (estudo mostra que isso reduz usabilidade sem aumentar segurança proporcionalmente — NIST SP 800-63B).

### 5. Auto-login após register
`register()` cria sessão automaticamente e retorna refresh token. Usuário não precisa fazer login separado após se cadastrar. UX melhor.

### 6. Cookie de refresh token lido automaticamente
`getRefreshTokenFromRequest` lê do cookie primeiro (produção), fallback para body (testes). Facilita testes sem precisar mockar cookies.

### 7. `extractMetadata` captura IP e User-Agent
Usado para auditoria. Não capturamos dados sensíveis. O AuditLog ainda passa por `redactSensitive()` que mascara qualquer campo sensível que possa ter chegado por engano.

### 8. `handleAuthError` centraliza resposta de erro
Trata 4 tipos de erro:
- `ZodError` → 422 com `details` (path + message por campo)
- `ValidationAuthError` → 422 com `details`
- `ConflictAuthError` → 409
- `AuthError` → 401 com mensagem genérica
- Outros → 500 "Erro interno do servidor" (não vazar stack trace em prod)
