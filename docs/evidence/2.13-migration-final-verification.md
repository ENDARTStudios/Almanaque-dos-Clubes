## Decisões técnicas

### 1. `migrate deploy` (não `migrate dev`)
`migrate deploy` é o comando correto para ambientes não-dev. Diferenças:
- **`migrate dev`**: pode resetar o banco se houver drift, pede prompt para criar migration nova
- **`migrate deploy`**: apenas aplica migrations pendentes, falha se houver drift sem intervenção

### 2. Fallback para `prisma db execute`
Nem todo ambiente Windows terá `psql` instalado. `prisma db execute --stdin` faz o mesmo (lê SQL do stdin, executa no banco via Prisma). Trade-off: mais lento (cada statement em round-trip separado) mas não requer cliente psql.

### 3. `-DryRun` para validação prévia
Operador pode rodar `pwsh ./scripts/migrate.ps1 -DryRun` para validar que:
- DATABASE_URL está definida
- Container Docker está rodando
- pnpm está instalado
- node_modules existe

Sem aplicar nada. Útil para smoke-test antes de deploy.

### 4. Scripts em PowerShell (não Bash)
Stack do projeto: PowerShell no Windows (Operador) + Bash no Linux (Doer). Os scripts `migrate.ps1` e `verify-migration.ps1` são específicos para Windows. Equivalente bash pode ser criado no futuro se necessário.

### 5. Migration em pasta separada `migrations-postgres/`
Não colocamos a migration PostgreSQL em `prisma/migrations/` porque essa pasta é usada pelo SQLite sandbox (migrations SQLite lá ficam). Pasta separada `migrations-postgres/` deixa claro que é para PostgreSQL only.

Para aplicar manualmente:
```bash
psql "$DATABASE_URL" -f prisma/migrations-postgres/20260720000001_phase2_final/migration.sql
```

Ou o Operador roda `migrate.ps1` que faz isso via `prisma migrate deploy`.
